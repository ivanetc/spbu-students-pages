# Контракт сквозного примера для будущего конспекта и слайдов

## Предметная область

Продолжение уже знакомой студентам модели университета из `lecture_06.md`, §§1–4. `UniversityGroup` — record с проверенным непустым именем и равенством по нему; `Student` — обычный объект с ID, именем, группой и изменяемым статусом. В новом материале не переучивать модель и не создавать другой учебный мир.

## Четыре запроса к одним данным

1. `List<Student> registrations = new ArrayList<>()`: сохранить последовательность записей на занятие, включая повторное появление того же студента. Показать `add`, `get`, `set`, удаление, обход.
2. `Set<UniversityGroup> groups = new HashSet<>()`: получить уникальные группы; два разных экземпляра `new UniversityGroup("24.Б11-мм")` схлопываются благодаря `equals`/`hashCode`.
3. `Map<Integer, Student> studentsById = new HashMap<>()`: искать студента по ID, показать замещение `put`, `containsKey`, `entrySet` и риск изменяемого ключа на контрпримере, не используя `Student` как ключ в основном сценарии.
4. `Deque<String> applications = new ArrayDeque<>()`: обработать две заявки FIFO через `offerLast`/`pollFirst`, затем показать LIFO через `push`/`pop` на отдельном новом контейнере.

## Как пример развивается на доске

1. После массива на 2 места появляется третья запись: сформулировать требования прежде выбора типа.
2. Одна и та же пара студентов демонстрирует различия `List`, `Set`, `Map`, `Deque`. Для `Set` важны две равные по имени группы, созданные отдельно.
3. Предсказать вывод `size`, `add` дубля и `put` повторного ID. Показать, что представление `entrySet()` связано с map, а не копирует записи.
4. Во второй половине не вводить новые предметные сущности: нарисовать хранение этих же записей как массив ссылок, цепочку узлов и корзины с коллизиями. Числовые hash и индексы корзин в диаграмме задать как *игрушечную модель*, не как реальные значения `String.hashCode()` или конкретные адреса памяти.
5. Закончить сравнением четырёх запросов и обоснованным выбором реализации.

## Границы

- Код совместим с Java 21; новые `Sequenced*` методы можно обозначить, но не делать зависимостью основного примера.
- До объяснения лямбд не использовать лямбда-выражения или method references в основном коде. Сортировку показать на `List<String>` естественным порядком и концептуально обозначить `Comparator` как стратегию собственного порядка; реализацию компаратора с лямбдой отложить до следующей лекции.
- Не обещать фиксированный порядок обхода `HashSet` или `HashMap`; ожидаемый вывод демонстрации не должен от него зависеть.
- `Student` не применять как хеш-ключ, поскольку модель изменяема и её равенство в существующей лекции не задано по ID.
